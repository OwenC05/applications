## 1. Outcome, boundaries and current evidence

Deliver one local Python application in which a tech or finance applicant can confirm personal evidence, add an exact vacancy, inspect original company/role research, generate grounded tailored answers, review exact wording and export it. In a **later separately gated browser release**, prepare supported forms and submit only after a distinct exact-payload approval. Every friend runs an independent installation; profile switching is not authentication or protection from other local OS users.

Existing strengths and gaps (paths relative to repository):
- `src/store.mjs:138–337` owns Node onboarding/memories/applications; `saveDraft:287` has optimistic guards; `recordApplication:314` records human review or a user-reported external submission, not a browser receipt.
- `src/server.mjs:131–155,179–247` checks consent each call, but its busy set is not durable. `src/ai.mjs:96–223` supplies bounded provider research/drafting; research excerpts are model text, not fetched source bytes. `src/context.mjs:2–16` is substring retrieval.
- `backend/copilot/contracts.py:5–130`, `store.py:47–69,218–301,352–405`, `retrieval/service.py:98–161`, `api.py:137–231` implement a separate evidence workbench, immutable confirmations, coherent hybrid indexes, exact citations and deletion. They lack the application domain, employer corpus, paid jobs, semantic support and browser delivery. Current owner-wide revision/index invalidation must not be reused for unrelated UI/application edits.
- `public/app.js:12,36–54` and `backend/ui/` are separate experiences. Preserve Node until Python parity is verified, not indefinitely maintain two sources of truth.
- `docs/plans/evidence-verification.md` reports 68 Python +73 Node tests and real-model/Chroma/browser checks, **not Docker execution or live answer quality**. Its 12-query benchmark found negation failure, no hybrid advantage and non-abstaining unanswerables. Existing quotations cannot be relabelled grounded generated answers.

Requirements inherited from `docs/plans/local-rag-{mvp,tests}.md`: Python/FastAPI; SQLite canonical; Chroma dense + BM25 + RRF + local reranker; immutable explicitly confirmed facts; deliberate imports; local ownership; explicit cloud opt-in; bounded costs; independent deletion/restore; exact citation inspection. New user request expands the old no-submission boundary only for the planned later browser release.

**MVP sequence:** A researched-grounded drafting → B supervised form preparation → C separately approved, receipt-tracked submission. No universal ATS coverage, automatic accounts/login, assessments, CAPTCHA bypass, demographic inference, bulk unattended applications, Trackr scraping, hosted friend accounts or hiring-success guarantees. English TXT/MD/text-PDF remains initial ingestion scope. Offline mode offers evidence, quotations, editing and export, not an invented local writing model.

## 2. RALPLAN-DR and architectural decisions

**Principles:** (1) Truth and explicit confirmation before persuasion. (2) Canonical versions and inspectable sources before autonomous actions. (3) Minimum disclosure and capability separation. (4) Fail closed on uncertainty; preserve recoverable work. (5) Ship measured vertical slices, not technology-count claims.

**Top drivers:** authentic company/exact-role specificity; preventing private-data leakage or incorrect/duplicate submissions; a usable independent local installation.

**Option A — selected: staged Python modular monolith.** One SQLite durable worker, private Chroma, bounded research tools, separate local headed browser companion later. Reuses existing Python retrieval, keeps state/transaction boundaries inspectable and avoids premature distributed coordination. Costs: port Node parity, own robust job fencing and package a companion.

**Option B — retain Node product, add Python retrieval/research sidecar.** Fastest near-term UI reuse and less migration initially. Costs: two domain authorities/revision protocols, cross-runtime deletion, credentials and job cancellation; diverges from requested Python backend. Useful only as a temporary parity harness, not product architecture.

**Option C — general autonomous browser agent plus distributed queues.** Broader exploratory navigation and scaling potential. Costs: larger permission/injection surface, opaque final-payload changes, operational overhead and no reliable universal ATS guarantee. Reject for initial local workload; reconsider specific components only after measured need.

**ADR browser deployment:** Prefer Docker API/worker/Chroma plus an explicitly installed **local headed Playwright companion**, exclusively owned automation profile, visible user login/handoffs. Compared with headed Docker/noVNC this avoids shipping a remote desktop/auth surface and awkward MFA/download access, but requires a second installation and tested Windows/WSL coordination. No browser debugger or noVNC port exposed. Companion initiates a paired, loopback-only authenticated connection; single-use pairing code requires explicit UI action, session token is short-lived/revocable and stored in OS-protected storage. Backend validates Host/Origin and capability-scoped messages; token possession is not permission to submit arbitrary destinations. Prefer polling requests over an unauthenticated companion HTTP listener. Prove Windows browser→Docker localhost connectivity before choosing packaging. If unavailable, release A with export; do not silently expose LAN services.

## 3. Freeze interfaces before parallel implementation

Use versioned Pydantic contracts and explicit SQLite schema migrations. UUID identities; UTC timestamps; SHA-256 hashes over documented canonical serialization; Unicode **code-point** offsets. Every record carries owner/profile ID; application-related records additionally application ID. Server checks ownership at every read/write, never trusts browser/model-supplied owner IDs.

| Contract | Required invariants |
|---|---|
| Profile/consent/interview | Typed contact/identity and sensitive answer records are separate from dense story retrieval, scoped to purpose/application/jurisdiction; never infer them. Profile metadata revision separate from `facts_revision`, document corpus revision, consent revision and application input revision. Skippable/resumable interview produces proposals; consent includes provider and disclosed purpose. |
| Proposal/fact version | Proposal pending/confirmed/rejected with origin. Immutable confirmed wording/hash, confirmation event/time, kind manual/interview/document-derived/legacy, optional original spans. Corrections create new version and supersede old. Raw personal documents are never automatically applicant facts. |
| Application/questions | Exact company, role, vacancy URL/ID, sector, explicit official domains; stable question IDs, required/type/word/character constraints and constraint origin. Role/questions edits increment input revision and invalidate dependent research/drafts/form plans. Pure UI/name edits do not rebuild fact indexes. |
| Source/research run | Corpus kind `personal_documents`, `confirmed_facts`, `employer`; employer scoped to owner+application+research run. Original bytes/hash, canonical text/hash, extraction version, exact/final URL, acquiredAt, provenance `public_fetch`, `anonymous_rendered_dom`, `user_supplied`, or `legacy_model_text`. Research completeness requires identifiable current exact role AND company source; inference separately labelled. |
| EvidencePacket | Per question/cover-letter requirement: query/criteria, confirmed fact version IDs and exact spans, separate employer source IDs/spans, retrieval generation/model/prompt versions, truncated/omitted/gap flags, captured revisions. Packet hash binds generation inputs; never include unselected raw personal docs. |
| Draft/support/review | Immutable draft revision and final text hash; answers keyed to exact question set. Ledger covers all factual spans, kind personal/employer/inference, citations and integrity, assessment state supported/unsupported/contradicted/needs_confirmation/unassessed. Review snapshot binds exact text, ledger, facts/source/input versions and disclosure. Review ≠ fact confirmation or submission. |
| Job/provider attempt | Idempotency key, stage, captured revision vector, lease/heartbeat, monotonically increasing fence, cancellation and bounded attempts. Provider reservation/attempt precedes send; statuses definitely-unsent/completed/indeterminate. All job-owned writes, including index publication, compare fence+revisions. |
| Form snapshot/field map | Adapter/version, destination origins, account identity indicator, vacancy identity, form/step revision, labels/types/options/required/limits, locator hints, conditional dependencies. Mapping binds question/answer/fact IDs or manual typed values; absent/ambiguous mapping is blocked. |
| Attachment/rendered payload | Explicit user-selected immutable prepared file, MIME/size/hash and accessible filename. Payload includes actual rendered field values/options/declarations, files/hashes, destination/account/vacancy and all steps. Hash the normalized semantic payload, including adapter-known applicant-affecting hidden/default fields, not raw HTTP bytes. Exclude opaque CSRF/multipart/transport fields only by explicit adapter allowlist; never expose these to models. Unknown hidden fields or opaque encoding require manual submission; action endpoint changes invalidate it. |
| Grants/submission attempt | Fill grant binds exact destination, fields/values/files/hash and expiry; **separate** one-use submit grant binds completed payload hash, form revision, review, account and destination. Durable attempt exists before click; unknown outcome cannot auto-retry. Receipt retains minimal confirmation/reference evidence and timestamp. |

Index manifests remain immutable, dense and BM25 same snapshot, with owner+corpus+application scope as applicable. Eligibility checks occur after retrieval, before every transmission and before final save. Add derived-dependency records so revisions invalidate affected packets/drafts/reviews/grants rather than globally reindex everything. No lock held during model/network/browser operations: short transactions capture state, leases allow work, transactional CAS/fence rejects stale results.

## 4. Milestone A: one researched-grounded drafting workflow

### Domain, migration and usable UI
Port existing onboarding, proposals, preferences, applications and review/history semantics to Python; strengthen semantic review gates without silently upgrading legacy status. An explicit chosen legacy export/import operation supports dry-run, schema validation, unchanged-source hash, backup, collision/repeat-import rejection and transactional commit. Do not auto-read `.env`/`.data`, merge profiles, overwrite legacy data or mint original-page provenance for historical research. Label legacy verified facts honestly; legacy reviewed/submitted events remain history, not current assessed drafts or receipt-confirmed submissions. Keep Node runnable on a separate port until parity/import/rollback tests pass. One Python-served UI incorporates evidence inspector and async job/progress/cancel screens; no dual writing. After each application, store immutable history/outcome/feedback and pending evidence or style-preference proposals. Generated prose, approval and receipts never self-confirm new facts or reinforce model-created assertions as personal truth.

### Bounded research agents
“Agent” means a role-specific model behind a deterministic tool broker, not arbitrary shell/browser autonomy. Discovery/research can issue bounded public searches, fetch allowlisted pages, and request a separately sandboxed anonymous render when static HTML lacks content. Public research sees company/role/questions, **never the personal brain, cookies, API key or authenticated browser state**. User confirms official company domains and supported ATS origins; do not guess lookalike domains. Access restrictions, login/paywall/CAPTCHA or missing exact vacancy produce an incomplete research report and manual-source/import option.

Baseline per run: at most 4 search operations, 10 fetched pages total (including at most 2 rendered pages), 2 MiB each, 100 PDF pages, 15s fetch/30s render, 120s overall network deadline; no recursive navigation beyond budget. Enforce HTTPS, exact host allowlists, port443, no URL credentials; resolve/check IPv4/IPv6, connect to validated destination without unchecked second resolution, validate every redirect. Route renderer **all** network/subresource/JS requests through equivalent egress policy, disable service workers/downloads/WebSockets or explicitly block them, isolate filesystem and strip credentials. Request interception alone is not a claim of complete network isolation: qualify network-level containment in tests. Reject private/loopback/link-local/metadata destinations, DNS rebinding and oversized streams. If safe rendering is not proven, static-only research remains available and JS-only sources remain incomplete.

Persist actual downloaded bytes and canonical spans. Rendered DOM records DOM capture/time/hash and network provenance; it is not the original HTML response, and neither is model-produced text. Source freshness initially seven days plus vacancy/input changes; closed/removed vacancy blocks readiness. Company values, role competencies and tech/finance priorities become a **sourced rubric**; “what a hiring manager wants” remains a labelled inference, never insider knowledge. Finance answers require evidence for analytical/commercial/regulatory claims just as tech claims require actual engineering evidence; no invented deals, returns or metrics.

### Evidence to drafts
Compile deterministic bounded query variants within the existing128-token retrieval limit: preserve negation and priority criteria, never concatenate an entire JD blindly. Keep the full original question and limits in the EvidencePacket; split long queries into bounded variants or request clarification when truncation would change meaning. Log truncation visibly. For each question separately retrieve confirmed facts and employer evidence from separate scoped generations; combine within token budgets. Explain chosen evidence and missing facts before generation. Pipeline: plan → draft → support/style critique → at most one rewrite → fresh final critique (3–5 generation calls). Research discovery/normalization has at most2 provider calls with tool-operation ceilings; no open-ended agent loops. Cap initial per-application generation at12 questions, each≤2,000 input characters and a24,000-token aggregate selected context ceiling; larger forms require explicit split/contracted budget rather than silent omissions. Individual output limits honor the question; cover letter default400words, user adjustable.

Provider SDK/model identity/pricing table pinned during execution and recorded with each run. Before launch show conservative token/call estimate and require configured local per-run/daily reservation ceilings; if no validated price mapping, enforce token/call limits and display monetary estimate as unknown. One durable worker reserves usage before each request; configure SDK automatic retries off for paid ambiguity. No consent/key means zero paid calls. Minimal selected spans only; redact content from logs, default no exported telemetry; disclose unavoidable provider retention limits.

Deterministic checks enforce exact question coverage, ownership/current versions, citation spans/hashes and word/character limits. Semantic assessment attempts complete factual-span coverage and exposes unassessed spans; this automated inventory itself is fallible and requires adversarial/human audit, not a formal exhaustiveness claim. It checks every identified factual claim against supplied evidence, including negation/quantities/leadership distinctions. Citations prove provenance, not entailment; model assessment remains fallible. Any unsupported/contradicted/unassessed/needs-confirmation factual span, invalid citation, missing required answer or exceeded limit blocks **review-ready**. The user can still save/edit/export blocked text with visible warnings, but cannot obtain an assessed/reviewed badge or automatic browser handoff. New personal facts become proposals only. Editing invalidates exact-text ledger; reassessment is at most1 consented call, no rewrite, revision guarded. Factual gap questions return to explicit confirmation then regenerate/reassess.

### Concurrent index ownership and recovery (R1, cycle 2)

S2 explicitly replaces the cross-process `data_lock` lifecycle in `config.py:28–47`, CLI recovery/build exclusion in `__main__.py:31–36`, API lock/startup recovery in `api.py:75–85,196–201`, and retrieval recovery/cleanup in `retrieval/service.py:174–201`, coordinating with S4. Simply removing the lock is unsafe: current recovery deletes unpublished generations and owner-wide cleanup can delete newer work. Current `store.py:247–272` also invokes tokenization inside a write transaction and replaces corpus-global chunks before build success; both must change.

1. In a short SQLite transaction capture immutable canonical source/fact versions and relevant revisions, and register a unique generation staging intent **before any external artifacts**. Intent binds owner/corpus/application, generation, job, fencing token, lease, exact owned collection/path identities, model/chunker identity and input snapshot hash. Release transaction/global lock before loading models, tokenizing, embedding, dense/sparse building or waiting on IO; status and cancellation must remain responsive while these stall.
2. Validate computed chunks against the captured immutable text and persist immutable **generation-specific canonical chunk associations**, never replace another generation's chunk set. Stage dense and sparse artifacts in generation-exclusive names/paths. State transitions are `registered → building → ready → published`, or `abandoned → cleanup_pending → cleaned`; transitions require current operation ownership. Retired published generations remain explicitly registered until safe cleanup.
3. After both indexes and chunk associations validate, publish their single manifest with captured-revision, job/lease and fence CAS. S4 publication depends explicitly on this S2 ownership contract. A failed rebuild, including changed chunking, retains the preceding eligible manifest **and its original chunk set**. This is not permission to serve superseded/deleted facts: if canonical evidence eligibility changed, the old generation remains unavailable until rebuilt; retained artifacts are only a rollback option when still eligible.
4. Recovery protects every published eligible generation and live leased staging intent; it must not delete an artifact merely because it is unpublished. Expired/reclaimed attempts lose publication authority and their generation is abandoned. Do not reuse its generation/paths for a newer fence. Record abandonment and generation-scoped cleanup claims transactionally, then clean only captured owned paths/collections; revalidate cleanup ownership before destructive operations. Never sweep an owner's entire directory or collections for an older ticket. Profile deletion additionally tombstones that owner to prohibit new generation registration.
5. External writes from an expired process may finish late despite fences. Its permanent generation identity/tombstone makes those late artifacts discoverable and ineligible; repeat conservative reconciliation after producer quiescence, and retain cleanup intent until verified absent. Cancellation/reclaim terminates or quarantines owned stage processes when possible; do not claim physical cleanup complete while a live producer can recreate artifacts. Restart recovery uses the same registered ownership graph, not active-manifest-only guessing. Unknown artifacts are reconciled against all registrations and quarantine/age policy before removal, never mistaken for another live job. Old cleanup can never target a newer registered generation.

### Recovery, retention and deployment
Durable SQLite worker precedes paid research/drafting and long indexing. Pause indeterminate prepared/transmitted attempts; keep their reservations until reconciliation, never infer unused budget from lease expiry. Explicit warned retry creates a new attempt; auth/quota errors never auto-retry. Revocation stops subsequent calls, cannot recall already sent bytes. Restart/cancel preserves previous drafts. Fence staging outputs/manifests as well as final records. Upload intents prevent orphan recovery deleting active work; deletion tombstones block late jobs and clean sources, facts, generated prose, employer indexes, form plans and grants. Source deletion defaults to revoking linked facts; preservation requires new standalone confirmation. Physical cleanup stays pending until verified.

Compose adds worker; API only `127.0.0.1`, private dedicated Chroma, non-root/pinned images, secret mounts only where needed, no credentials in images/logs/exports. Retention controls distinguish active history, deletions and externally retained provider/backups/downloads. SQLite consistent backup plus referenced blobs; restore into empty instance, verify hashes, rebuild indexes, disable cloud and invalidate grants/browser sessions. Docker runtime and two independent installations are release gates, not supplied by YAML validation.

## 5. Later browser release: B prepare, then C submit

**Initial adapter:** Greenhouse hosted application form, capability-limited and versioned, selected because public job/question documentation supports fixtures. Lever second after Greenhouse gates. Public GET APIs may assist discovery; employer-authenticated POST APIs are **not** applicant submission APIs, and no employer key extraction is allowed. Unsupported/custom/Workday flows remain manual export; publish tested template/step limits rather than claiming every Greenhouse employer works.

B: user starts visible companion and navigates an approved vacancy. User handles login/MFA/CAPTCHA, assessments and sensitive declarations. Dedicated profile only, no existing Chrome-profile import or cookies passed to models. Discover labels/options/constraints and multi-step conditional fields; new questions feed back to application drafting before writing. If revealing later steps requires personal data, obtain a scoped fill grant first: filling/uploading can autosave/transmit **before Submit**. Schema-only redacted field information may go to a model only with cloud disclosure; never full authenticated pages. Typed deterministic mapping first, model suggestions never execute unvalidated actions. Sensitive eligibility/demographic/legal declarations are manual or explicitly user-confirmed typed values, never inferred; assessment execution remains manual.

Every fill grant shows origin, vacancy/account, fields/values and attachment hashes; expire in15minutes, revoked by content/account/domain change. Use strict role/label locators and visible readback; ambiguous/hidden/new fields, unsupported input widgets, security challenges and destructive actions stop for human handling. Do not force clicks or take first locator match. Classify actions by adapter-known network mutations (kind, method/path, destination/account), never by button label: Continue may create or finalize an application. Unknown action semantics require manual handoff. Deny unapproved egress, service workers and unsupported WebSockets; page JS/autosave is not exempt from transport policy. Fill grants cannot authorize final endpoints. **Before forwarding every applicant-data-bearing outbound request**, the adapter normalizes its semantic content and compares it with the active fill grant: only an exact approved field/value subset and approved attachment bytes/hash may pass, bound to owner/operation, account, destination, vacancy and declared step. This covers query strings, navigation requests, beacons, autosaves, uploads and intermediate transitions regardless of HTTP method—not only POSTs. Validate grant expiry/revocation and active operation at this transmission boundary. Explicitly allowlist transport-only fields; altered values, extra applicant data, unknown fields or unsupported/opaque encoding are denied before transmission, then require manual handoff. Legitimate partial autosaves may pass only if every transmitted semantic item is approved. Origin/path allowlists and post-fill DOM readback alone are insufficient. This governs supported automated transmissions; do not promise control of every manual action outside companion automation. MVP attachments are user-reviewed PDF CV and optional exact reviewed cover-letter artifact, not a CV-rewriting/DOCX engine. Use immutable approved upload copies and hash their actual transmitted bytes to prevent path/file TOCTOU; a changed file requires new grant. Approving a CV artifact does not confirm every CV statement into the brain. Browser UI makes transmissions/side effects visible and supports abort, not a false promise of rolling back remote autosave.

C: only after all steps are discovered/completed and rendered readback matches reviewed answers does the user see final summary and authorize **this exact application**. Submit grant expires in5minutes, one-use, binds payload/form/review/account/origins. Immediately revalidate and capture readback; changes/new fields invalidate approval. Intercept the supported final request and revalidate its normalized semantic payload against approval before forwarding; opaque/unrecognized fields or encoding require manual submission. Mark grant consumed and durable submission attempt prepared before the single adapter-owned final action. Block duplicate final transport attempts, including identifiable page-XHR retries, within that adapter; do not claim exactly-once remote execution. A crash after preparation is conservatively unknown. Never automatically retry a click or replay on restart/timeouts. “Clicked”, navigation or HTTP200 is not receipt proof: persist adapter-validated explicit confirmation/reference, with minimal redacted page evidence; otherwise `submission_unknown` and reconcile via visible portal/manual confirmation. Manual report is `user_reported_submitted`, never `receipt_confirmed`. Block a second attempt while unknown; explicit reviewed reconciliation can unlock a new attempt with duplicate-risk warning. No email-account access added for receipt lookup.

## 6. Deliberate pre-mortem and release decisions

1. **Plausible false application:** a relevant but negated chunk or old role supplies a persuasive false claim. Mitigate frozen adversarial retrieval/support evals, separate corpora, complete span ledger, exact-source inspector and human review. Fail release on invented qualification/result; no unsupported badge.
2. **Leak/duplicate action after crash:** prompt injection changes destination; autosave leaks data; lease recovery rebills/submits again. Mitigate capability-separated research/browser, before-fill disclosure, exact grants, fenced jobs, durable attempts and unknown-stop behavior. Verify with malicious fake ATS and process-kill matrices.
3. **Friends cannot run/recover it:** migration overwrites data, Docker memory or companion pairing fails, deletion leaves derivatives. Mitigate non-destructive import, tested restore/cleanup, bounded resources and two independent setup trials; ship A/export without B/C if browser gates fail.

A release requires semantic retrieval/support quality, Node parity, Docker/recovery/privacy and browser UI gates. B release separately requires fake-ATS discovery/fill, credential isolation and autosave-consent gates. C requires exact-grant/unknown-outcome/receipt fault tests and independently reviewed adapter actions. Tests never submit to real employers; a future live pilot requires a separate explicit user authorization for that exact application. No calendar/hiring outcome promise.
